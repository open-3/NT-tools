> 版本：v0.1（草案，待评审）｜ 日期：2026-11-11 ｜ 状态：**仅设计，未开发**
>
> 关联仓库：`D:\资料\AI\状态跟踪\app`（Agent Pulse）

---

## 1. 一页纸摘要

给 Agent Pulse 工具箱新增一个 **「局域网通信」工具**，让同一局域网内的多台电脑能：
1. **聊天**：文字消息实时互发（点对点 + 群发可看到在线列表）。
2. **传文件**：把文件（含目录/图片/任意二进制）发给局域网内的某个或某几个对端。

定位为**免配置、即开即用的内网协作小工具**，不依赖公网服务器、不注册账号、不碰云盘。

---

## 2. 问题与机会（Problem Statement）

### 2.1 背景
Agent Pulse 现在的工具箱里有一批"单机小工具"（JSON 格式化、时间戳、端口进程…），
全是**本机自用**。但在实际办公场景里，同一个局域网内经常有多台电脑之间要
"临时传个文件"或"说一句话"：

- 传文件现在靠微信/QQ（要登录、要公网、有大小限制、文件可能被转储压缩）；
- 或者靠 U 盘、网盘（要手动、慢、要下载客户端）；
- 或者临时开共享目录（要配置、暴露面大、用完忘了关）。

### 2.2 机会
用户在"程序员协作 / 内网办公"场景下，缺一个**轻量、免账号、点开就能用**的
局域网点对点通信工具。Agent Pulse 作为常驻桌面的工具聚合器，天然适合承载它
——不用再开一个新软件。

### 2.3 目标（非目标）

**目标（In scope）**
- 同一局域网内 Agent Pulse 实例互相发现（自动显示在线设备）。
- 一对一文字聊天（实时）。
- 广播/群发文字消息。
- 一对一 + 一对多文件传输，带进度、断点提示、完成后可"打开所在目录"。
- 传输安全：同一内网默认可见，但对敏感内容提供**一次性配对码 / PIN 确认**机制。

**非目标（Out of scope，v1 明确不做）**
- 不做公网/跨局域网（不架中转服务器、不打洞穿透）。
- 不做账号体系、历史云同步、多端消息漫游。
- 不做语音/视频、群聊持久群组管理。
- 不做文件夹完整同步（那是网盘/rsync 的活），只做"发文件/文件夹"。
- 不承诺端到端加密到行业安全标准（内网明文 + 可选 PIN，够用但不吹 E2EE）。

## 4. 产品形态（Product Decisions）

### 4.1 决策：做成「工具箱里的一个新工具」，而不是改主浮窗
- 主浮窗的职责是"只读聚合 Agent 会话"，塞聊天会污染职责、拉高复杂度。
- 工具箱已有成熟的多窗口 + preload + 独立页面 + 独立图标体系，新工具零侵入接入。

### 4.2 决策：对端身份 = "对方的 Agent Pulse 实例"
- 通信发生在 **Agent Pulse 客户端之间**（A 机器装了 Agent Pulse ↔ B 机器装了 Agent Pulse）。
- 这是最容易实现也最贴合"常驻工具"定位的方案，且能复用现有 appId / 设备命名逻辑。
- v1 **不**做"给一个非 Agent Pulse 设备发"（那需要通用协议/网页端，复杂度翻倍）。

### 4.3 决策：发现机制 = UDP 组播 + 本地唯一 ID
- 靠 UDP 组播（multicast）在局域网广播"我在这"的心跳，自动发现同网段其他实例。
- 每个实例有稳定唯一 ID（首次运行生成 UUID，存本地 store），用于去重和身份识别。

### 4.4 决策：必须先明确一个待用户拍板的关键选择

> ⚠️ **下面是影响整个设计形态的分叉，建议在设计评审时先敲定。**

| 问题 | 选项 A | 选项 B |
|---|---|---|
| 通信对端 | 只有装了 Agent Pulse 的机器（同应用互通） | 标准局域网协议（任意设备/网页/手机都能进） |
| 效果 | 实现快、体验统、复用现有 UI | 通用性强，但要兼容第三方实现，协议要更规范 |
| 推荐 | ✅ **v1 先做 A** | 留到 v2 跨端 |

（本方案正文按 **选项 A** 展开；若用户选 B，请看第 9 节「差异影响」。）

## 5. 功能需求（Functional Requirements）

### 5.1 在线发现（Discovery）
- `FR-1`：启动后自动加入组播发现，周期（如每 3s）广播心跳。
- `FR-2`：实时展示在线设备列表：设备名、IP、在线时长、是否在传文件。
- `FR-3`：设备离线（3 个心跳周期约 9s 无响应）自动标记为离线，可选保留或隐藏。
- `FR-4`：本机显示为「本机」，并且允许用户设置一个易读的**显示名**（默认＝主机名）。

### 5.2 文字聊天（Chat）
- `FR-5`：点某个在线设备 → 打开一对一聊天窗口。
- `FR-6`：发送/接收文字消息，消息带时间戳与发送方。
- `FR-7`：未读消息在设备列表 / 托盘 / 任务栏有角标或气泡提示。
- `FR-8`：广播消息：勾选多个设备（或"全体在线"）后群发，各端收到同一条广播。
- `FR-9`：聊天记录本地保存（SQLite，复用项目已有的 `node:sqlite` 只读/读写能力），重启后可回看。

### 5.3 文件传输（File Transfer）
- `FR-10`：拖拽或点选文件到聊天窗口 → 发送给当前对端（一对一）。
- `FR-11`：支持发**文件夹**（自动打包或逐文件发送，v1 建议逐文件+目录结构，避免内存爆）。
- `FR-12`：接收端可设置保存目录（默认 `%USERPROFILE%\Downloads\AgentPulse`），可"询问每次"。
- `FR-13`：传输进度条（百分比 + 速率 + 剩余），发送/接收双端都能看到。
- `FR-14`：传输完成/中断/失败有明确状态；失败支持一键重试。
- `FR-15`：接收完成后可"打开所在目录"。
- `FR-16`：同名文件处理：自动重命名（`file (1).ext`）或询问覆盖，默认自动重命名。

### 5.4 安全与确认（Security）
- `FR-17`：局域网内默认可以看到彼此，但**首次发文件/消息时**可选要求对方通过一个
  **配对码（PIN）**确认，防止隔壁工位误连。
- `FR-18`：传输可以关闭（全局开关"加入局域网发现"），关闭后本机既不广播也不接收。

## 6. 非功能需求（NFR）

| 维度 | 要求 |
|---|---|
| 性能 | 文字消息 <100ms 到达；文件传输打满局域网带宽（百兆/千兆） |
| 文件大小 | v1 目标支持单文件 ≥ 2GB（分块流式，不整段进内存） |
| 内存 | 传输过程内存占用恒定（≤ 32MB 缓冲），不随文件大小增长 |
| 稳定性 | 中途断网/对端离线 → 明确失败并可重试，不崩溃、不丢半截文件 |
| 隐私 | 不将任何消息/文件内容上传到公网；日志不含正文 |
| 兼容 | Windows 10/11 x64（沿用现有 Electron 45 基线） |
| 资源占用 | 空闲时 CPU ≈ 0，心跳/发现开销 < 1% |

## 7. 技术设计（Technical Design）

### 7.1 总体架构

```
┌────────────────────────── Agent Pulse 主进程（Node 22）─────────────────────────┐
│                                                                                 │
│  ┌──────────────┐   ┌──────────────┐   ┌─────────────────────────────────────┐ │
│  │ Discovery     │   │ ChatService  │   │ TransferService                     │ │
│  │ (UDP 组播)     │◄──┤ (TCP/消息)   │◄──┤ (TCP 分块流式)                        │ │
│  └──────┬───────┘   └──────┬───────┘   └──────────────────┬──────────────────┘ │
│         │                  │                              │                     │
│         │                  └──────────────┬───────────────┘                     │
│         ▼                                 ▼                                     │
│  ┌───────────────────── LAN IPC 桥（ipcMain.handle + webContents.send）────────┐ │
│  └─────────────────────────────────────────────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────────────────────┘
          │                              ▲
          │ ipcRenderer.invoke           │ webContents.send / onUpdate
          ▼                              │
┌────────────────────── 工具窗口「局域网聊天」渲染层（vanilla DOM）───────────────┐
│  设备列表 ｜ 聊天区 ｜ 文件拖拽 ｜ 进度条 ｜ 设置（显示名/保存目录/PIN）           │
└──────────────────────────────────────────────────────────────────────────────────┘
```

- **主进程**承担所有网络 I/O（TCP/UDP），因为渲染层 `nodeIntegration:false` 无法直接建 socket。
- **渲染层**只负责 UI 与通过 `window.tool` / 新增的 `window.lan` API 收发事件。
- 复用现有工具箱的窗口 + preload + 独立图标体系，零侵入主浮窗。

### 7.2 发现协议（Discovery — UDP 组播）

- 固定组播地址：`239.255.42.99:45317`（项目内约定，避免与常见服务冲突）。
- 心跳包 JSON：
  ```json
  {
    "v": 1,
    "type": "hello",
    "app": "agent-pulse",
    "id": "<本机 UUID>",
    "name": "张三的台式机",
    "tcpPort": 45318,
    "ts": 1730000000000
  }
  ```
- 每 3s 发一次，TTL=32（限制在本地网内）。
- 收到任意新的 `id` → 加入在线表；超过 9s 未再收到 → 标记离线。
- node 端用 `dgram`（UDP）实现，无需额外依赖。

### 7.3 连接与消息（TCP + 自定义帧）

- 每个实例监听一个 TCP 端口（如 45318，或动态端口再通过心跳告知）。
- 通信帧用「4 字节长度前缀 + JSON 头部 + 负载」：
  - 文字消息：JSON 头 `{type:"msg", id, ts, text}`。
  - 文件：控制头 `{type:"file", name, size, mime, totalChunks}` + 二进制分块。
- 连接管理：按对端 `id` 维护连接池，避免重复连接；懒连接（要用才连）。
- 文字消息靠 TCP 保证可靠序；文件传输在同一 TCP 流上分块。

> 备选：也评估过 WebSocket（`ws` 包）vs 原生 TCP。结论 v1 用**原生 `net` 模块**
> 即可（零新依赖、协议自定最灵活）；若后续要跨端才上标准 WebSocket。

### 7.4 文件传输（分块流式）

- 发送端：`fs.createReadStream` 分块（如 256KB）读 → 写 TCP socket，边读边发；
  内存恒定，单文件支持 >2GB。
- 每块带序号，收端按序写 `fs.createWriteStream` + 校验字节数。
- 进度：已发字节 / 总字节，主进程每 100ms 推一次 `onProgress` 事件到渲染层。
- 中断：socket `error`/`close` 时标记失败，保留 `.part` 临时文件；重试 = 重新发起
  （v1 不做断点续传的中断点恢复，只做整文件重发，避免状态机复杂度）。
- 文件夹：递归枚举，先发清单（相对路径树），再逐文件发送；收端按清单重建目录。

### 7.5 数据存储（本地 SQLite）

- 复用项目已引入的 `node:sqlite`（Node 22 内置）。
- 表设计（草案）：
  - `peers(id TEXT PRIMARY KEY, name TEXT, ip TEXT, last_seen INTEGER)`
  - `messages(id INTEGER PK, peer_id TEXT, dir INTEGER, text TEXT, ts INTEGER)`
  - `transfers(id INTEGER PK, peer_id TEXT, dir INTEGER, name TEXT, size INTEGER, state TEXT, path TEXT, ts INTEGER)`
- 存储位置：`%APPDATA%\agent-pulse\lan.db`（与现有 store 同级）。

### 7.6 IPC / preload 扩展（新增 `window.lan` API）

在 `src/tools/preload.ts` 之外，为局域网工具提供一个**专用 preload**（或复用 + 新的命名空间），暴露：

```ts
window.lan = {
  // 生命周期与发现
  start(): Promise<{ ok: boolean; port: number }>
  stop(): void
  getPeers(): Promise<Peer[]>
  setName(name: string): Promise<void>

  // 聊天
  sendText(peerId: string, text: string): Promise<void>
  broadcast(text: string): Promise<void>
  onMessage(cb: (m: Message) => void): void

  // 文件
  pickAndSend(peerId: string): Promise<void>          // 主进程弹选择框
  sendPath(peerId: string, path: string): Promise<void>
  setSaveDir(dir: string): Promise<void>
  onTransfer(cb: (t: TransferEvent) => void): void    // 进度/完成/失败
  openSavedDir(): Promise<void>                        // 打开接收目录
  onPeersChanged(cb: (peers: Peer[]) => void): void
}
```

主进程新增 `src/main/lan/` 目录（`discovery.ts` / `chat.ts` / `transfer.ts` / `store.ts` / `ipc.ts`），
在 `main.ts` 启动时按需初始化（懒启动：首次打开工具才 start，减少常驻开销）。

### 7.7 工具注册

- 在 `src/main/tools.ts` 的 `TOOLS` 数组加一行：
  ```ts
  { id: 'lanchat', label: '局域网通信', icon: '🛜', size: { width: 760, height: 720 } }
  ```
- 新建 `src/tools/lanchat/{index.html,index.ts,style.css}`，走现有构建管线。
- 生成对应图标进 `build/icons/lanchat.ico`。

### 7.8 安全边界

- 默认**不加密**（内网明文），但：
  - 传输前可选 PIN 确认（一次性配对码，两端口头确认）。
  - 全局开关「加入局域网发现」可关闭，关闭后彻底不下线外也不收。
- 明确在 UI 里提示"内网明文，请勿用于敏感数据"。
- v1 不引入端到端加密（代价高，收益对内网场景低），作为明确非目标写进文档。

### 分阶段交付（建议迭代顺序）

1. **M1 最小可用**：发现 + 连接 + 文字一对一聊天。（先验证"能互相看到、能说话"）
2. **M2 文件传输**：单文件流式发送/接收 + 进度 + 保存目录。
3. **M3 体验完善**：广播、文件夹发送、本地历史、在线角标、PIN 确认、打开目录。
4. **M4（可选）**：跨端/标准协议、断点续传、端到端加密。

## 9. 若选「选项 B」（通用局域网协议）的差异影响

如果拍板"任意设备都能连"，则：
- 发现与消息协议需切换为**标准可解析**格式（如基于 mDNS/DNS-SD 或 SSDP 的服务发现，
  消息走 WebSocket + JSON 固定 schema），并发布协议说明文档。
- 需要提供"网页端/命令行"等至少一个非 Agent Pulse 的端点作为对照实现。
- 工作量显著增加（估计 4~6 人日起），且要先承诺协议稳定性。

**建议：v1 先做选项 A（Agent Pulse 互通），协议设计时预留 `v` 字段和可扩展头，
为 v2 兼容标准协议留后路。**
